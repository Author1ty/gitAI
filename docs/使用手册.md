# Git AI Insight Dashboard 使用手册

## 1. 产品简介

Git AI Insight Dashboard 是一个基于 **Git AI Notes** 的代码归因分析平台。它由单个 Spring Boot 程序提供页面和 API：后台读取仓库的 `refs/notes/ai` 及 `git ai stats <commit> --json` 信息，持久化提交级归因数据，并以看板方式展示 AI、人工、混合和未知/未追踪代码的统计结果。

系统按照“部门 → 项目 →（可选）仓库分组 → 仓库”组织数据，适合查看个人、项目、仓库分组和部门维度的 AI 代码使用情况。

> 归因来自 Git AI 提供的证据。**未知/未追踪不等于人工代码**；它只表示 Git Note 未提供足够的可确认归因信息。

## 2. 核心功能

- **代码归因总览**：AI 归因、人工确认、混合归因、未知/未追踪代码行及提交数、已纳入统计的仓库数。
- **趋势与分布**：每日归因趋势、AI 参与度、部门分布、项目排行、仓库明细与 AI 工具贡献。
- **个人排名**：按 Git 提交者统计“AI 生成代码行”和“AI 代码占比”两个榜单。
- **全景视图**：项目、仓库分组两个维度的汇总与排行。
- **多维筛选**：日期范围、部门、项目、仓库分组、仓库；筛选会同步作用于看板指标与表格。
- **数据源管理**：维护部门、项目、仓库分组、仓库及仓库 Git 地址。
- **手动同步**：将仓库同步任务入队，由后台 Git Worker 异步执行。
- **同步任务**：查看任务状态、阶段、进度、错误和历史记录。
- **定时同步**：配置是否启用及执行间隔；后台会按间隔创建同步任务。
- **运营管理**：账号、角色、部门、审计日志及管理概览。

## 3. 角色与权限

| 角色 | 看板与同步任务 | 数据源管理、手动同步 | 自动同步、运营管理 |
| --- | --- | --- | --- |
| 最高权限（`SUPER_ADMIN`） | 可查看 | 可配置、可触发 | 可配置、可管理 |
| 部门权限（`DEPARTMENT_ADMIN`） | 仅本部门范围 | 可管理本部门、可触发同步 | 不可访问 |
| 查看权限（`VIEWER`） | 只读查看 | 不可配置、不可触发 | 不可访问 |

当前认证是三方认证的**占位适配器**：系统仅将用户名与密码交给认证适配器，不保存密码。开发演示账户如下，密码填写任意非空值：

| 用户名 | 角色 |
| --- | --- |
| `superadmin` | 最高权限 |
| `deptadmin` | 部门权限 |
| `viewer` | 查看权限 |

生产上线前必须替换 `ExternalAuthenticationClient` 对接企业统一认证，并关闭占位认证。

## 4. 环境要求

- JDK 21；
- Node.js 20 或更高版本（仅在构建前端时需要）；
- Git；
- 已安装 Git AI，且运行服务的操作系统用户能访问其 `bin` 目录；
- 生产环境：MySQL 8.x 与足够的磁盘空间（用于 bare mirror）。

默认 Git AI 工具目录为 `${user.home}/.git-ai/bin`，可用环境变量 `GIT_AI_BIN_DIR` 修改。

## 5. 构建与单 JAR 启动

前端构建产物会被 Spring Boot 打包进最终 JAR。部署时**只需启动一个 JAR**，不需要单独部署 React 或 Node.js 服务。

### Windows 构建

```powershell
cd frontend
npm ci
npm run lint
npm run build

cd ..\backend
.\mvnw.cmd test
.\mvnw.cmd package
java -jar .\target\git-ai-dashboard-0.0.1-SNAPSHOT.jar
```

### Linux 构建

```bash
cd frontend
npm ci
npm run lint
npm run build

cd ../backend
./mvnw test
./mvnw package
java -jar target/git-ai-dashboard-0.0.1-SNAPSHOT.jar
```

默认访问地址：`http://服务器地址:8080/`。健康检查：`GET /api/health`，正常响应为 `{"status":"ok"}`。

开发默认使用文件型 H2 数据库：`./data/git-ai-dashboard`。H2 仅适合本地演示和开发，不建议用于生产。

## 6. MySQL 生产配置

先创建数据库和最小化业务账号（请替换强密码和主机限制）：

```sql
CREATE DATABASE git_ai_dashboard
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'git_ai_dashboard'@'localhost' IDENTIFIED BY '请替换为强密码';
GRANT ALL PRIVILEGES ON git_ai_dashboard.* TO 'git_ai_dashboard'@'localhost';
FLUSH PRIVILEGES;
```

然后通过环境变量启动：

```bash
export SPRING_PROFILES_ACTIVE=mysql
export MYSQL_URL='jdbc:mysql://127.0.0.1:3306/git_ai_dashboard?useUnicode=true&characterEncoding=UTF-8&connectionCollation=utf8mb4_0900_ai_ci&useSSL=false&serverTimezone=Asia/Shanghai'
export MYSQL_USER=git_ai_dashboard
export MYSQL_PASSWORD='请替换为强密码'
export GIT_AI_BIN_DIR='/home/gitai/.git-ai/bin'
export GIT_AI_MIRROR_ROOT='/opt/git-ai-dashboard/mirrors'
java -jar git-ai-dashboard-0.0.1-SNAPSHOT.jar
```

Flyway 会在启动时自动执行 MySQL 专用迁移（`db/migration-mysql`）。请确保运行用户对 mirror 目录有读写权限。

> **兼容性与升级说明**：生产目标为 MySQL 8.0+。MySQL 专用迁移显式使用 InnoDB、utf8mb4 和 `utf8mb4_0900_ai_ci`，不会写入 Windows 本地测试仓库、演示项目或虚构统计数据。该迁移集用于**新建的空 MySQL 数据库**；如果某个库曾用旧版本的通用/H2 迁移初始化，请先备份，并以新库初始化加数据迁移的方式升级，不能直接替换迁移文件后启动，以免 Flyway 校验历史记录失败。



## 实际 MySQL 验证（推荐在发布前执行）

项目提供了只在设置测试库环境变量时才启用的 `MySqlIntegrationTests`。它会用真实 MySQL 驱动执行 MySQL 专用 Flyway 迁移，并检查关键表、初始部门、账号和开发机路径未被写入。

> 测试库必须是独立的空 MySQL 8.0+ 数据库，严禁填生产连接串。

```powershell
$env:MYSQL_TEST_URL = 'jdbc:mysql://127.0.0.1:3306/git_ai_dashboard_it?useUnicode=true&characterEncoding=UTF-8&connectionCollation=utf8mb4_0900_ai_ci&useSSL=false&serverTimezone=Asia/Shanghai'

```

## 7. 看板使用

1. 登录后进入“代码归因总览”。
2. 在“统计范围”选择日期、部门、项目、仓库分组或仓库；层级筛选会限制后续可选项。
3. 查看顶部指标卡：AI 归因、人工确认、混合归因、未知/未追踪、提交次数、纳入统计仓库。
4. 向下查看趋势、AI 参与度、部门/项目分布、仓库明细和 AI 工具贡献。
5. 在“个人 AI 代码排名”切换：
   - **AI 生成代码行**：按 AI 归因代码行排序；
   - **AI 代码占比**：按 AI 行占已统计代码比例排序。
6. 在“项目与仓库分组全景”切换项目与仓库分组，查看汇总、仓库数、提交数及占比。

### 归因口径

| 指标 | 含义 |
| --- | --- |
| AI 归因 | Git AI Note 能明确确认由 AI 产生的新增代码行。 |
| 人工确认 | Git AI Note 能明确确认由人工产生或确认的新增代码行。 |
| 混合归因 | 同一代码行同时具有 AI 和人工来源时计入。不同代码行分别属于 AI、人工不构成混合。 |
| 未知/未追踪 | Note 缺少足够归因证据；不能直接作为人工代码。 |

## 8. 数据源管理

最高权限和部门权限用户可点击顶部“管理数据源”。建议按如下顺序创建：

1. **部门**：填写部门名称和可选说明；
2. **项目**：选择所属部门，填写项目名称；
3. **仓库分组（可选）**：选择所属项目，填写分组名称；
4. **仓库**：选择项目和可选分组，填写仓库名称、Git 地址、默认分支及可选 mirror 目录。

仓库地址可以是服务器可访问的 HTTPS、SSH 地址，也可以是本机可访问的本地 bare 仓库路径。配置完成后点击顶部“同步 Git AI 数据”创建任务。

部门权限只能维护自己所属部门范围内的数据；查看权限没有此入口。

## 9. Git AI 数据同步

### 手动同步

1. 在看板顶部点击“同步 Git AI 数据”；
2. 系统创建异步任务并立即返回，不会让浏览器请求等待 Git 操作完成；
3. 在“同步任务”中跟踪状态、阶段、提交处理数量和失败原因；
4. 同一仓库如果已有排队或运行中的任务，会复用已有任务，避免重复 clone 或并发写入。

同步时系统维护 bare Git mirror，并读取 `refs/notes/ai` 和 `git ai stats <commit> --json`。它持久化提交 SHA、提交时间、Note 对象、归因行数及工具统计，再生成看板聚合数据。

### 任务状态与排查

常见阶段包括排队、准备 mirror、读取提交、读取归因、写入统计和完成。任务失败时先查看错误信息，重点检查：

- Git 地址从服务器是否可达；
- 服务账号是否有仓库 SSH/HTTPS 凭据；
- `GIT_AI_BIN_DIR` 是否正确，`git ai` 是否能被服务账号执行；
- Git AI Notes 是否位于 `refs/notes/ai`；
- mirror 目录磁盘权限和剩余空间；
- MySQL 连接、表迁移和容量是否正常。

## 10. 定时同步

仅最高权限用户可进入“自动同步”。

1. 打开“自动同步”；
2. 启用开关；
3. 设置执行间隔（5 分钟至 7 天）；
4. 点击“保存自动同步设置”。

保存后，后台调度器会在下一次检查时（默认一分钟内）按设定间隔为仓库创建同步任务。定时同步仍受同步队列和并发限制保护，不会绕过任务机制。

## 11. 运营管理

最高权限可使用“运营管理”：

- **概览**：查看运营与系统概览；
- **账号**：新增、编辑、启用或停用用户，并分配角色、部门；
- **角色**：查看三种内置角色及权限范围；
- **部门**：查看部门信息；
- **审计日志**：追踪登录、数据源配置、同步及账号管理等敏感操作。

停用账号后该账号无法再次登录；权限不足的用户即使直接调用 API，也会被后端拒绝。

## 12. 大仓库保护与容量建议

面向数百万行、数年历史的大仓库，请先小范围验证，**不要第一次就无约束地同步全部历史**。默认保护配置如下：

```yaml
git-ai:
  command-timeout: PT2M
  clone-timeout: PT15M
  max-commits-per-sync: 500
  max-command-output-bytes: 67108864
  sync:
    worker-count: 1
    queue-capacity: 10
```

对应环境变量：

```bash
export GIT_AI_COMMAND_TIMEOUT=PT2M
export GIT_AI_CLONE_TIMEOUT=PT15M
export GIT_AI_MAX_COMMITS_PER_SYNC=500
export GIT_AI_MAX_COMMAND_OUTPUT_BYTES=67108864
export GIT_AI_SYNC_WORKER_COUNT=1
export GIT_AI_SYNC_QUEUE_CAPACITY=10
export GIT_AI_SYNC_SCHEDULE_CHECK_DELAY=PT1M
```

建议：

- 先在测试副本上同步一个仓库，观察 mirror 占用、CPU、磁盘 I/O、网络和 MySQL 写入；
- 保持 `worker-count=1`，确认资源富余后再逐步提高；
- 将 `max-commits-per-sync` 保持为较小批次，通过多次同步逐步消化历史；
- 为 mirror 和数据库预留容量，避免与业务工作区共用紧张磁盘；
- 将定时同步放在业务低峰期，并监控失败任务和队列积压。

## 13. Linux 原生部署（无 Docker）

建议目录：

```text
/opt/git-ai-dashboard/
  git-ai-dashboard.jar
  mirrors/
  logs/
```

创建 `/etc/systemd/system/git-ai-dashboard.service`：

```ini
[Unit]
Description=Git AI Insight Dashboard
After=network.target mysql.service

[Service]
Type=simple
User=gitai
WorkingDirectory=/opt/git-ai-dashboard
Environment=SPRING_PROFILES_ACTIVE=mysql
Environment=MYSQL_URL=jdbc:mysql://127.0.0.1:3306/git_ai_dashboard?useUnicode=true&characterEncoding=UTF-8&connectionCollation=utf8mb4_0900_ai_ci&useSSL=false&serverTimezone=Asia/Shanghai
Environment=MYSQL_USER=git_ai_dashboard
Environment=MYSQL_PASSWORD=请替换为强密码
Environment=GIT_AI_BIN_DIR=/home/gitai/.git-ai/bin
Environment=GIT_AI_MIRROR_ROOT=/opt/git-ai-dashboard/mirrors
Environment=GIT_AI_SYNC_WORKER_COUNT=1
Environment=GIT_AI_SYNC_QUEUE_CAPACITY=10
Environment=GIT_AI_MAX_COMMITS_PER_SYNC=500
ExecStart=/usr/bin/java -jar /opt/git-ai-dashboard/git-ai-dashboard.jar
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

启用服务：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now git-ai-dashboard
sudo systemctl status git-ai-dashboard
curl http://127.0.0.1:8080/api/health
```

如需用 Nginx 提供 HTTPS 和域名访问，可反向代理 `/` 到 `http://127.0.0.1:8080/`。因为前端已经打入 JAR，不需要额外配置静态前端目录。

### 自动化测试

```powershell
cd backend

cd ..\frontend
npm run lint

```

### HTTP 回归脚本

仓库提供 `scripts/Test-GitAiDashboard.ps1`。对已运行的实例进行只读验证：

```powershell
.\scripts\Test-GitAiDashboard.ps1 -BaseUrl http://127.0.0.1:8080
```

`-IncludeWriteTests` 会创建部门、项目、仓库分组、仓库及测试账号，应仅在隔离的 H2/MySQL 测试库运行：

```powershell
$repo = (Resolve-Path .\test-repos\git-ai-attribution-sample-remote.git).Path
.\scripts\Test-GitAiDashboard.ps1 `
  -BaseUrl http://127.0.0.1:18080 `
  -IncludeWriteTests `
  -RepositoryUrl $repo `
  -SyncTimeoutSeconds 90
```

该仓库同时提供小型 Git AI 样例仓库用于真实同步验证。大仓库性能样本应仅用于受控压测，不应放入普通回归流程。

### 多部门、多仓库、多提交人真实同步回归

`New-GitAiMultiDimensionFixture.ps1` 会生成可重复的本地 Git AI 测试仓库；`Test-GitAiDashboardMultiDimension.ps1` 会创建组织、仓库和同步任务，再等待真实 Git 同步完成后校验看板与权限。它覆盖：

- 2 个部门、4 个项目、4 个仓库分组、6 个仓库；
- 24 条业务提交，日期为 **2026-08-12 至 2026-08-15**，包含单日筛选；
- Alice、Bob、Carol 三名提交人；
- AI、人工、混合、未知/未追踪四种归因，以及 cursor、copilot、aider 等工具；
- 部门、项目、分组、仓库、日期筛选；部门管理员的数据隔离与查看权限禁止触发同步；
- 同步任务历史完成状态、运营概览与审计日志。

> 脚本会写入部门、项目、分组、仓库、同步任务和测试账号，**只能连接隔离的 H2 或专用测试 MySQL 数据库，绝不能对生产库执行**。

```powershell
# 1) 生成或重建六个本地 bare Git 测试仓库
.\scripts\New-GitAiMultiDimensionFixture.ps1 -Force

# 2) 在隔离实例上执行真实同步和回归检查
.\scripts\Test-GitAiDashboardMultiDimension.ps1   -BaseUrl http://127.0.0.1:18081   -SyncTimeoutSeconds 180
```

测试看板时，请将“昨天”理解为实际业务提交日期：本测试数据中的昨天是 **2026-08-15**；`refs/notes/ai` 自身的维护提交不计入业务提交统计。

## 16. 常见问题

**Q：读取 Git 信息会下载完整代码仓库吗？**  
A：系统维护 bare Git mirror。首次同步需要获取仓库 Git 对象，后续通过 fetch 做增量更新；它不是每次重新 clone 完整工作区，但 mirror 仍需按仓库规模预留磁盘空间。

**Q：需要单独启动前端吗？**  
A：不需要。执行前端构建并 Maven 打包后，静态前端资源已包含在单个 Spring Boot JAR 中。

**Q：为什么看板没有数据？**  
A：确认仓库已创建、同步任务已成功、仓库包含可读取的 Git AI Note，并检查筛选条件是否过滤了数据。

**Q：查看权限为什么不能点击同步或配置？**  
A：这是预期行为。查看权限只能读取看板和任务列表；前端隐藏写操作，后端也会强制拒绝未授权请求。

**Q：能否直接把大仓库的全部历史一次同步完？**  
A：不建议。应利用默认的 500 提交批次、单 Worker 和队列限制分批同步，在副本或低峰时完成容量与性能验证后再扩大规模。
